點對點直連（不經過中繼伺服器）延遲最低、頻寬最好，但兩台機器之間通常隔著**有狀態防火牆**和 **NAT**。這篇整理 NAT 穿透的完整做法：從最基本的防火牆打洞，到困難 NAT、中繼、ICE 的路徑選擇，最後是企業與雲端環境的實務建議。內容以 Tailscale 的公開技術文章為主要依據，來源列在文末。

## 問題：兩邊都在等對方先開口

幾乎所有防火牆（Windows 防火牆、ufw、AWS Security Group、家用路由器）的預設規則都是「**允許往外，擋掉沒被請求的往內**」。對 UDP 來說，意思是：只要我先送過一個封包給 `B:port`，之後從 `B:port` 回來的封包就會被放行。

客戶端連伺服器沒問題，因為客戶端總是先開口。但兩台都在防火牆後面的機器互連時，雙方都在等對方先送封包，而先送的那一方的封包會被對面的防火牆擋掉，結果就是誰都連不上。

## 解法一：兩邊同時送

關鍵在於防火牆規則只要求「**我這邊先送出過**」。所以讓兩邊**大約同時**互送封包：

1. A 送給 B，封包被 B 的防火牆丟掉，但 **A 的防火牆已經記下這條連線**。
2. B 送給 A，同理，B 的防火牆也記下了；而且這個封包會被 A 的防火牆當成「回應」放行。
3. 兩邊的防火牆都有狀態了，之後封包雙向暢通。

這招有三個前提：

- **要知道對方的 `ip:port`**：需要一個「側通道」（協調伺服器）交換位址。這個通道很省：延遲幾秒沒關係，總流量只有幾 KB，一台小伺服器就能服務上千台機器。
- **時間要對得上**：兩邊得在對方的防火牆狀態還在時送出，所以也靠側通道協調時機。
- **要定期保活**：防火牆會忘記閒置的 UDP 連線，常見的逾時是 30 秒左右，所以要持續送 keepalive。

另外有兩個前提條件：協定**必須是 UDP**（TCP 也能穿，但難很多；需要串流就在 UDP 上跑 QUIC），而且程式要**能直接控制收發封包的那個 socket**，因為穿透用的封包必須和正式流量走同一個 socket。

## NAT 讓問題更難：你不知道自己在外面長什麼樣

NAT 是會改寫位址的防火牆。筆電 `192.168.0.20:1234` 送封包出去時，家用路由器把來源改成公開的 `2.2.2.2:4242`。問題是：**這個對外的 port 是送出封包當下才決定的**，筆電自己不知道，也就沒辦法告訴對方。

### STUN：問別人「你看到我是誰」

STUN（RFC 8489）的做法很直接：向一台公開伺服器送個請求，伺服器回答「我看到你的來源是 `2.2.2.2:4242`」，再把這個位址透過側通道告訴對方。

要注意的是，**問 STUN 的 socket 必須就是之後傳資料的 socket**，因為 NAT 對每個 socket 各建一組對應，換一個 socket，對外的 port 就不一樣了。

### 簡單 NAT 與困難 NAT

STUN 有一個隱含假設：**STUN 伺服器看到的 port，就是其他人看到的 port**。這個假設不一定成立：

| | 對應行為 | STUN 有沒有用 |
| --- | --- | --- |
| **簡單 NAT** | 不管連到哪裡，都用同一個對外 port（endpoint-independent mapping） | 有用，家用路由器多半是這種 |
| **困難 NAT** | 每個目的地各開一個新 port（endpoint-dependent mapping） | 沒用，STUN 看到的 port 只對 STUN 伺服器有效 |

教科書常用的 Full Cone、Restricted Cone、Port-Restricted Cone、Symmetric 這四種分類已經過時，比較準確的是 RFC 4787 的兩個獨立維度：**對應行為**和**過濾行為**。同時互送的技巧可以應付各種過濾行為，**真正決定成敗的只有對應行為**，所以對穿透來說，分成「簡單／困難」兩類就夠了。

### 困難 NAT 都在哪裡

困難 NAT 集中在三個地方，也正是穿透最常失敗的地方：

- **企業防火牆**：越標榜「安全」的設備，越可能是困難 NAT。各家的預設不同：
  - **pfSense／OPNsense**：底層的 FreeBSD PF 預設是困難 NAT。2024 年底已有修補讓 PF 支援簡單 NAT 的對應方式，但要等路由器發行版收進去才用得到。
  - **Sophos**：預設保留來源 port，對穿透友善。
  - **Palo Alto**：PAN-OS 11.1 起有「Persistent NAT」選項可以開啟。
  - **UniFi**：入侵防護規則預設可能把 P2P 流量判定成威脅直接擋掉。
- **CGNAT**：ISP 在用戶家的 NAT 外面再包一層，後面會細談。
- **雲端 NAT 閘道**：

| 雲端 | NAT 閘道的行為 |
| --- | --- |
| **AWS NAT Gateway** | 一律是困難 NAT，每個目的地隨機分配來源 port，無法調整 |
| **Azure NAT Gateway** | 預設是困難 NAT，沒有可以調整的設定 |
| **Google Cloud NAT** | 預設是困難 NAT；改用**靜態 port 分配**時是簡單 NAT，代價是每台 VM 固定佔用一段 port，擴展性受限 |

所以**兩台都躲在雲端 NAT 閘道後面的機器，幾乎不可能直連**，這點在設計雲端架構時要先想到。

## 穿不過去時：中繼

遇到困難 NAT，很多實作就直接宣告失敗。正確的做法是**永遠準備一條退路**：兩邊都連得到的中繼伺服器，由它轉送封包。代價只是延遲高一點、頻寬可能小一點，而且只有直連失敗時才需要。

中繼還有一個不可取代的理由：有些網路幾乎擋掉所有對外 UDP，例如只放行 DNS 的訪客 Wi-Fi，這時只能靠中繼。

傳統的中繼協定是 TURN（RFC 8656）。Tailscale 的設計可以當成很好的參考，它把中繼分成三層，依序嘗試：

**直連 → Peer Relay → DERP**

| | DERP | Peer Relay |
| --- | --- | --- |
| **誰營運** | Tailscale 營運的共用中繼 | 自己網路裡的任一台機器 |
| **傳輸** | TCP over TLS，通常走 443 port | UDP，只需要開一個 port |
| **優點** | 最嚴格的網路也擋不住 | 可以放在要連的資源旁邊，吞吐量接近直連 |
| **缺點** | TCP 增加延遲，共用頻寬有限制 | 兩邊都要連得到那個 UDP port |

- **DERP** 依公鑰轉送已加密的封包，中繼本身看不到內容；它**同時也是側通道**，交換位址、協調打洞都經由它。它是最後的備援，不會被取代。
- **Peer Relay** 只替同一個網路、且有權限的節點轉送。早期合作客戶測到的吞吐量接近直連；有一個跨國連線的案例，從 DERP 的約 2.2 Mbps 提升到 27.5 Mbps，但這是單一個案，不是正式的基準測試。

在 STUN、同時互送，再加上中繼備援的組合下，**九成以上的連線可以直連**。

## 進階技巧：處理剩下的困難案例

### 生日悖論：猜中困難 NAT 的 port

一邊是簡單 NAT、另一邊是困難 NAT 時，簡單的一方知道對方的 IP，但不知道 port。暴力掃完 65,535 個 port，以每秒 100 個封包計算，最壞要 10 分鐘，還很像 port scan，容易觸發入侵偵測。

改用生日悖論：困難的一方開 **256 個 socket**，簡單的一方隨機猜 port。只要有任何一對對上就成功：

| 簡單端送出的探測數 | 成功率 |
| --- | --- |
| 174 | 50% |
| 256 | 64% |
| 1,024 | 98% |
| 2,048 | 99.9% |

以每秒 100 個封包計算，一半的情況 2 秒內就連上，20 秒內幾乎一定成功，而且只掃了不到 4% 的 port。這正好對應最常見的「家裡連公司」「家裡連雲端」：家用路由器多半簡單，公司和雲端閘道多半困難。

但**兩邊都是困難 NAT 時就不實際了**：雙方的來源 port 都是隨機的，搜尋空間變成平方。要達到 99.9%，每邊大約要送 17 萬個探測，約 28 分鐘。而且大量探測會塞爆 NAT 的連線表，例如 Juniper SRX 300 的上限是 64,000 條連線，一次暴力嘗試就可能吃光。這種情況直接走中繼。

### Port mapping 協定：直接請路由器開門

有三種協定可以請本地閘道「把某個對外 port 轉到我這裡」：

- **UPnP IGD**：1990 年代的設計，XML 加 SOAP，實作複雜，歷史上有過嚴重漏洞，但最普及。
- **NAT-PMP**（RFC 6886）：Apple 設計，只做 port 轉發，簡單。
- **PCP**（RFC 6887）：NAT-PMP 的後繼。

成功的話等於「加強版 STUN」：既知道自己的公開位址，NAT 也會對所有人開放這個 port，困難 NAT 也變成可以穿。

問題是這些協定常被關掉，許多設備用一個勾選框同時關掉三種，連比較安全的 NAT-PMP 和 PCP 也一起關了。UPnP 本身的安全疑慮也讓它越來越不可靠，所以更根本的解法是 **NAT 設備本身採用簡單 NAT 的對應方式**，port mapping 只當加分項。

實作上還有一個細節：路由器重開機後，之前建立的 mapping 會消失。客戶端應該偵測這件事（NAT-PMP 和 PCP 的回應裡有一個 epoch 值，重開機後會歸零），並自動重建 mapping，而不是默默掉回中繼。

### 雙層 NAT 與 CGNAT

- **雙層 NAT**：對穿透來說大致無感，因為對方只看得到最外層。但 port mapping 會失效，它只能請離你最近的那層 NAT 開門。
- **CGNAT**：ISP 在用戶家的 NAT 外面再包一層，讓很多家庭共用少數 IPv4。特殊的狀況是**兩台機器在同一個 CGNAT 後面**：STUN 回報的是最外層位址，要互連得靠 NAT 支援 **hairpinning**（把送往自己公開位址的封包繞回內部）。很多 NAT 不支援，這時又只能走中繼。

### IPv6：沒有 NAT，但還有防火牆

IPv6 位址夠用，不需要 NAT，STUN、生日悖論、port mapping、hairpinning 都可以省掉。但**有狀態防火牆還在**，所以同時互送、側通道和中繼仍然需要。

IPv6 的普及也還不夠：Google 的統計到 2026 年 3 月才第一次在單日超過 50%，而且各地差異很大。所以 IPv6 只能當成多一條路，不能取代 IPv4 的整套做法。

只有 IPv6 的網路會用 NAT64 和 DNS64 連到 IPv4 世界。手機通常有 CLAT 把這層藏起來，桌機和伺服器則要程式自己查詢 `ipv4only.arpa` 偵測 NAT64 前綴，這是比較少見的情況。

## 全部組起來：ICE 的思路

每個網路環境適用的技巧都不同，**逐一判斷網路型態再對症下藥是做不完的**。ICE（RFC 8445）的核心思路是：**全部同時試，挑最好的那條**。

1. **收集候選位址**：區網 IPv4、IPv6、STUN 查到的公開位址、port mapping 拿到的位址、管理者手動設定的位址。
2. **透過側通道交換候選清單**。
3. **對每個候選位址送探測封包**：探測同時有兩個作用，一是打開 NAT 和防火牆的狀態，二是當作經過驗證的 ping/pong，量測每條路徑通不通。
4. **挑最好的路徑**：傳統 ICE 依類型排序（區網優先，其次公網，最後經過 NAT）。更好的做法是直接用**實測的往返延遲**排序，結果通常一樣，但不必靠猜。

幾個實務上的取捨：

- **不必等探測結束才開始傳資料**：連線一開始先走中繼，資料馬上就能傳；同時在背景找更好的路徑，通常幾秒內就升級成直連。
- **路徑斷了就降級**：例如 NAT 重開機、狀態被清掉時，先退回中繼，再重新找一次路徑。這比隨時維持備用路徑簡單。
- **端對端加密是必要的**：路徑會變，就不能靠 IP 判斷對方是誰。如果上層協定本身已經加密，例如 WireGuard 或 QUIC 的 TLS，偽造的探測最多只能把流量繞遠路。即使如此，探測封包本身也應該驗證和加密。

## 企業與雲端環境的實踐

- **預設公司網路那一端會穿不過去**：企業閘道是最常失敗的地方。設計 P2P 功能時，要把中繼當成正常路徑的一部分來規劃，而不是例外。
- **雲端主機別只靠 NAT 閘道**：需要點對點直連的機器，依優先順序可以這樣處理：
  1. 給它一個公開 IPv4（例如 AWS 的 Elastic IP），並開放 WireGuard 的 UDP port，最好只對自己其他節點的 IP 範圍開放。關鍵基礎設施最建議這樣做。
  2. 自己架 NAT instance，或用設定成簡單 NAT 的 pfSense／OPNsense。
  3. GCP 改用靜態 port 分配。
  4. 前面放一個 UDP 負載平衡器（AWS NLB、Azure Standard LB），但這不是官方支援的做法。
  5. 最後手段：在 VPC 裡放一台中繼。
- **自架中繼比繞到外部好**：在網路邊界或 VPC 裡放一台 UDP 中繼，防火牆只要開**一個**例外，整個辦公室或 VPC 就不必繞到外部的共用中繼，延遲和頻寬都好很多。
- **最後的備援要走 HTTPS**：最嚴格的網路只放行 DNS 或 HTTP(S)，所以最外層的中繼要跑在 TLS 443 上，而且要盡量靠近使用者，降低繞路的延遲。
- **檢查防火牆的 NAT 與 IPS 設定**：確認是否能開啟簡單 NAT 的對應方式（例如 Palo Alto 的 Persistent NAT），以及入侵防護規則有沒有把 P2P 流量當成威脅。
- **管理 UPnP 時分開看**：UPnP 有安全疑慮，但 NAT-PMP 和 PCP 相對單純。設備允許的話，不必一個勾選框全關。
- **別把生日悖論當日常手段**：它會吃掉連線表，看起來也像 port scan，可能觸發 IDS。多台機器在同一個閘道後面同時這樣做，會拖垮閘道。
- **閒置逾時要算進去**：企業防火牆的 UDP 逾時可能很短，keepalive 的間隔要比它短。
- **身分驗證不能靠 IP**：所有路徑都要端對端驗證和加密。

## 檢查清單

- **需要的東西**：UDP 協定、能直接控制 socket、一個跟對方溝通的側通道、幾台 STUN 伺服器、一組中繼伺服器（強烈建議同時有 UDP 中繼和走 HTTPS 的備援中繼）。
- **步驟**：
  1. 列出本機所有網卡的 `ip:port`。
  2. 問 STUN 取得公開位址，順便判斷是簡單還是困難 NAT。
  3. 嘗試 port mapping 協定，並在路由器重開機後重建。
  4. 有 NAT64 的話，經由它取得 IPv4 公開位址。
  5. 透過側通道交換位址和金鑰。
  6. 先經由中繼開始傳資料。
  7. 對所有候選位址送探測，必要時用生日悖論處理困難 NAT。
  8. 依「直連、自架中繼、共用中繼」的順序選路徑；找到更好的就無縫升級，斷了就降級。
  9. 全程端對端加密和驗證。

沒有任何單一技巧能穿透所有 NAT。**把所有技巧疊起來，再配一個永遠可用的中繼，才能做到「不管在哪裡都連得上」。**
